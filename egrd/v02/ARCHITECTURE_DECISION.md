# EGRD_V02_AUDIT_COMPLETE_MORE_EVIDENCE_REQUIRED

**Select no new production mechanism for implementation yet.** This is an audit
completion, not an instruction to create another optional Skill or a research-only
controller. All production candidates remain frozen.

The observed stop mechanism is clear: full output reservation leaves 15360 input
tokens and new source/diagnostic history exceeds it. However:

1. Almost no read overlap or message insertion duplication exists. A lossless
   repeated-read deduplicator has little demonstrated target content to remove.
2. Context-cap expansion already removed guard stops without another native
   success in the prior matched pilot, while increasing cost.
3. Semantic evidence compaction could remove necessary new code, not merely
   duplicates. Exact tokenizer/template replay is unavailable locally and the
   pinned competitor interface does not expose global history projection.
4. The supported history switch retains this task's current tool chain. Callback
   names have no executable registry in the pinned Runner. Host-side compaction
   would be research infrastructure unless an organizer-supported path is proved.
5. Evidence-state/checking Skills already exist and were not used. Adding another
   optional helper does not resolve that bottleneck. An earlier correct edit or
   a lost supported patch is not established; patch-search complexity is premature.

## Single next diagnostic priority

**Evidence-preserving context projection feasibility**, rather than a new Agent.
First obtain an approved copy of the exact tokenizer/template and replay all 40
counts locally, then establish whether the organizer exposes a competitor-usable
history/compaction hook. This is one narrow feasibility question, not permission
to alter the Runner. A source-window/provenance-retention projection is only a
candidate after that path and its evidence-loss behavior are validated.

The smallest available offline continuation would compare annotated retained
evidence against original archived bodies using the exact rendering, preserving
Issue, current source/patch identity, contradictory observations, unresolved
questions and the latest tool-call/result pairs. Token savings alone would not
establish semantic preservation or repair efficacy. There is no new production
implementation or approved candidate artifact in this task.

## GO conditions and rejection criteria

Implementation GO requires a supported deployable hook, an identifiable removable
context burden beyond the near-zero duplicates, an explicit preservation policy,
CPU fault tests and a matched falsifiable study. If the only practical change is
more Prompt instructions or unsupported host interception, reject it. If no
projection preserves the decision-relevant evidence at useful cost, prefer a
small diagnostic study of contract/reproducer quality over implementing M1–M5.

Expected runtime/token overhead is **unknown** because no selected production
mechanism exists. A future deterministic projector would use CPU work over
history and no additional model call by design, but this is an assumption to
benchmark, not a measured latency promise. A target of≤1 second total projection
CPU per Session could be an acceptance budget, not a performance result. Existing
Skill-interface overhead 800 initial tokens is measured and should not be ignored.

The absence of an implementation GO does not prove all executable mechanisms
are forbidden or ineffective. It means this specific evidence does not yet
justify one with a verified competition path and useful preservation policy.
No S0 replacement, GPU experiment or official submission is recommended now.
