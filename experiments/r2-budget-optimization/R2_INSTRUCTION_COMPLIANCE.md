## Why no get_status?

The trajectory demonstrates non-use, not the model's reason. Initial system/user messages expose the static limits. The actual SDK low-budget warning attaches remaining **call counts**, not time; R2 receives them in all three sessions. No R2 run_command obtains the current time or a reliable global/session elapsed clock. Implicit time estimation, prompt ambiguity and sampling are plausible explanations, not established causes. The three R2 sessions still submit with time left, so a measured repair loss caused specifically by not querying status is not demonstrated. Lack of dynamic time evidence is a risk, not a fabricated observed failure.

The real official get_status was CPU-exercised on an eight-minute/28-call context: it returns local remaining seconds/calls and patch metadata, not global seconds or future task count. It does not debit a charged call. Model inference after calling it can still consume time. A rule that required frequent redundant status calls could make the Agent slower; a rule that never checks time can also fail on long operations. No ablation resolves that tradeoff yet.

## Why no explicit git diff?

Every R2 production edit returns a diff in edit_file's actual tool response. The last edit's diff therefore exposes the final small hunk. Full-patch internal collection occurs inside submit_patch; the CPU contract confirms git add -N and git diff --binary. Its response displays only size/file count, not full diff text or a correctness judgment. Reading that hunk, reading changed source, and cognitively reviewing it are not the same event; cognitive review remains UNKNOWN.

R2's final patches are clean by independent review; no observed R2 loss is attributable to the missing explicit command. However, local edit hunks cannot reveal unrelated untracked diagnostics. R1 Django first submits two files and later correctly removes its script/resubmits one file. BASELINE xarray receives status ok for zero bytes twice. This is evidence for a production-scope/nonempty check, not evidence to require redundant diff commands after an unchanged validated patch.

## Conflicts and what an ablation could establish

The inherited instruction to edit by a numbered call even when unsure conflicts with evidence-supported repair and with allowing enough time for necessary diagnostics. Baseline's at-most-two verification calls also conflicts with the need to correct malformed verification or revalidate a changed production version. These conflicts were present during all arms; do not silently repair the frozen control.

Candidate A proposes changing one inherited edit-decision bullet to an evidence threshold. Candidate B proposes changing only R2 rule 6 to version-bound closure. They are alternatives and are not combined. Rules 2/3/5 partly duplicate supplied limits and host guards; their marginal benefit, cost and whether they merely add prompt tokens are UNKNOWN. A future preregistered ablation is required to answer that question. No instruction is declared causally effective or useless solely from these three outcomes.
