# Two minimal research directions — design only

No Agent YAML, candidate ZIP, R3 or modified R2 is created. The exact frozen R2 remains the control. Each design has one explicit changed decision rule; A and B are not combined. Quantitative expected net savings are UNKNOWN. Historical time windows are optimization opportunities, not recoverable seconds.

## Candidate A: R2-Early-Decision — recommended first

Observed failure/opportunity: R1 xarray reads for the full deadline without editing; BASELINE xarray reaches malformed/budget-rejected edits after prolonged inspection. R2 has an early source-testable causal hypothesis, but its first production edits occur at about 256/326/134s. On pytest, BASELINE edits at 92s. These observations motivate a decision-threshold hypothesis but do not prove when the model already had enough evidence to edit.

One proposed factor: in a future derivative only, replace the inherited CALL PLAN bullet that mandates editing by call 12 and making a best guess when unsure. Leave all six R2 rules, all other prompt text, model/tools/schema/sampling/budgets unchanged. The replacement would define one evidence-gated edit decision: after identifying the implicated production path, a concrete causal hypothesis, and one bounded discriminating counterexample/comparison supporting it, choose the smallest reversible production change as the next repair action; if those conditions are absent, continue focused disambiguation rather than edit blindly. Preserve necessary target/control verification after the change. This is a decision-policy replacement, not an additional compulsory earlier timer or a new tool.

This explicitly resolves the inherited blind-edit conflict within the same changed bullet. It does not assume every early hypothesis is correct, use a task-specific fix, or inject R12 patch content. A proposed experiment must freeze the exact final replacement and hash the derived full prompt before running; this audit supplies no executable candidate.

Potential benefit: shorten hypothesis-to-edit delay and reduce later request/context pressure; the R2 observed windows are about 185s (Django), 311s (xarray) and 116s (pytest) from initial observable hypotheses. They include useful work and cannot be advertised as savings. Six invalid test constructions also identify an opportunity to ground evidence in the actual path rather than copying alternate implementations. Net cost/token change is UNKNOWN; one rule can add prompt tokens while reducing generated discussion, or do the opposite. The goal is not a shorter prompt.

Correctness risk: a false evidence threshold may encourage premature patches, anchoring, missed duck-array/migration/default controls or editing from a stack summary without reproduction. The threshold must not treat an unexecuted theory, failed fixture or copied function as actual production validation. Tests/controls are retained; no unconditional first-edit deadline is introduced.

Support metrics: paired Native Resolved and independently Validated Repair must be preserved/improved; generation seconds per correct repair, observable decision-to-edit interval, successful source-bound tests, malformed tools, request/summary counts and complete tokens per repair are secondary. Faster first edit alone is insufficient.

Refutation: lower native/semantic correctness, more wrong or reverted production changes, no reduction in generation cost per repair, merely moving time from pre-edit to repeated post-edit correction, or improvement only on the reused R12 tasks. A hypothesis supported only by fewer calls or a CPU scripted model is not accepted.

## Candidate B: R2-Submission-Efficiency — secondary, not selected for the next pilot

Observed opportunity: R2 Django deliberately removes/restores a patch after a passing but limited production assertion. R1 Django submits a diagnostic file first and then correctly cleans/resubmits; this is a sequencing issue, not justification to omit cleanup. Older Action-First fastapi_14786-A has repeated unchanged diff/submission after a first success. Conversely, R2 already has zero post-submit tool calls and no empty final submissions, so a universal further closure gain is weakly supported.

One proposed factor: replace only R2 rule 6 in a future derivative with a version-bound closure rule. When the smallest actual-production target check and required controls support the current production/test-input version, inspect complete patch scope once, remove unrelated diagnostics, submit a nonempty production patch and finish without optional re-investigation. Reuse evidence only while production/test inputs are unchanged; any change invalidates that evidence and requires the relevant check again. Every other R2/base-prompt rule and all runtime configuration remain fixed. This is one finalization-decision mechanism, not a new host controller, a combined A+B treatment or a change to budgets.

Potential benefit: fewer avoidable patch reversals or premature mixed-scope submissions. The R2 Django reversal/test cycle and associated HTTP costs are documented, but its first passing assertions do not establish the full DB/control endpoint. It would be wrong to claim every second after 315.978s is removable. No numerical net savings is defensible. Context/wording may increase tokens; the actual effect must be measured.

Correctness risk: stale validation reused after changes, an incomplete smoke promoted to a success, skipped compatibility controls or a model ending without checking untracked scope. Removing a corrective submit alone leaves the wrong patch. The mechanism must retain scoped checks and revalidation whenever necessary.

Success requires at least equal native/semantic repairs and lower full generation cost per repair, not just fewer submits. It is refuted if scope pollution/stale-test errors grow, it adds a diff/status inference round without repair benefit, it only reduces already-empty R2 post-submit activity, or it causes premature submission. R2's good submit rate leaves less headroom than Candidate A's early decision stage.

No R3, no R1+R2 merge, no third compaction/cache/model intervention is proposed. SDK compaction and hosting remain frozen. The evidence supports a single-factor pilot of A; it does not demonstrate either candidate's efficacy or justify a formal submission.
