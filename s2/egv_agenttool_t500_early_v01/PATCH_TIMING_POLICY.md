# Patch timing policy

Soft, unvalidated guidance through the existing get_status tool:0-150s locate and form a falsifiable hypothesis;150-230s choose a supported minimal edit or a scoped pre-repair EGV check if uncertainty blocks progress;350-400s assess essential checks and closure. These are Main instruction heuristics, not external scheduling or enforceable stages. Correctness takes precedence; an early wrong edit is negative evidence.

Repeated reads/tests are allowed when source, hypotheses or missing information change. Avoid repeated identical searches, overlapping dumps, redundant diagnostic scripts and print-only success claims without incremental evidence. Sparse status checks early/before delegation/closing reduce polling overhead. The native500s deadline and60 counted-tool limit remain unchanged.

CPU near-deadline tests offset the native context clock to approximately30s remaining to test skip-and-submit control flow. Separate exact-budget tests perform an actual approximately500s native wait and cancellation on the new candidate. Do not confuse these two kinds of timing evidence.
