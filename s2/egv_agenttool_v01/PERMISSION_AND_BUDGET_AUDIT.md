# Permission, accounting and cancellation boundaries

One SwegemmaContext owns both roles' charged-tool counters, task clock and workspace. CPU traces expose actor/tool/args/start/end/counter-before-after/file hashes; native tool output and HTTP lifecycles remain separate. Free get_status and submit_patch, uncharged AgentTool wrappers, counted inner official tools, model calls and HTTP dispatches are different numbers. Do not describe sixty as a hard ceiling on all raw function-call events.

The candidate has one300-second native Agent allowance, not300 per role. Initial CPU deadline/exhaustion fixtures use accelerated3-second/3-count boundaries; final budget01 additionally executes the actual300-second native deadline and60-count limit. Actual deadline300.098s cancels the pending child HTTP request;5 dispatches/4 received responses, missing final usage=null/partial, cleanup complete. Actual60-count fixture denies charged operations in both Main and child, with raw71 tool events/74 mock dispatches and a free submit of the still-wrong initial Patch. Its successful regression assertion does not mean repair success. Native regressions also retain Patch checkpoint, JUnit and cleanup tests. The declarative submission remains300/60/120.

Actual CPU03 disproved an immediate-stop assumption: exhaustion is checked between outer Runner invocations. Within the current invocation, further counted operations return BudgetExceeded without changing source or incrementing above the cap, but model calls, AgentTool wrappers, free status and free submission can continue. The scripted native fixture ultimately submits its still-wrong initial Patch with count3 and no native Agent error. This is a real negative result, not a successful repair. Time remains a separate hard enclosing limit. Reserve checks are necessary but do not guarantee autonomous cooperation. The near-deadline fixture advances the same clock to about30 seconds remaining, skips delegation and really submits; no additional time is allocated to the child.

EGV has no edit_file/write_file/submit_patch schema and cannot recursively delegate. A real negative CPU Shell command still changes production app.py; before/after hashes detect it. **The architecture is auditable, not forcibly read-only.** The observer does not undo writes, block commands, intercept results to help Main, or change official scoring. A production write in future GPU execution is an architecture violation and must block an algorithm-success claim; preserve its native Patch and decide using preregistered safety STOP rules.

Child tool errors and scoped FAIL/UNKNOWN reports are algorithm observations, not generic infrastructure faults. Missing result delivery, unresolved request terminal, loss of JUnit/native result, unknown provenance, sandbox contamination, failed cleanup or unaccounted resource usage are integrity faults. A missing model response has null usage; a reported zero from a native placeholder is not a measured zero.

Cancellation testing separates a returned command TimeoutExceeded from parent cancellation while the child HTTP request is pending. The latter records real CancelledError/terminal_status=cancelled and propagation to native deadline or caller; tests then verify worker/sandbox termination. This does not prove server-side request abortion. Future GPU must additionally meet the registered idle metric gate, retain exported backend logs and avoid inventing request-specific abort acknowledgements.

Logging snapshots can impose additional IO cost on large repositories. The same passive observer standards apply to both architectures; any B-specific delegation-boundary overhead belongs to B's net cost. This prototype's synthetic timing does not validate overhead on full repositories. No perfect isolation, guaranteed per-child deadline, or unmeasured cost saving is claimed.
