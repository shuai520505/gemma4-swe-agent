# Budget, progress and termination boundaries

Candidate settings are300s Agent wall clock,60 counted tools and120s maximum command time. They inherit official S1 configuration;300s is a conservative research starting point, not an optimality claim. Internal0–45/45–170/170–245/245–300s intervals are soft advice only. The model should use get_status around important strategy changes, not generate a stream of status calls.

Prompt-inducible behavior includes selecting useful tests, reserving closure time, recognizing an unchanged check, stopping an unproductive diagnostic path, checking a suspect test expectation, cleaning owned scratch files, and producing final text immediately after successful submission. These are not enforced by a submitted Python controller: there is no Python in the candidate ZIP.

Real enforceable public native constraints are the configured total task deadline, counted-tool cap, command timeout and legal tool schema, as exercised in the final CPU acceptance. Free get_status and submit_patch are distinguished from counted tools; model requests are a different counter. Command errors and a first assertion/no-match result are not automatically wasted actions. Deadline/cancellation evidence preserves null usage for unfinished responses and patch checkpoints before cleanup.

The pinned organizer source and negative CPU fixture show that successful submit_patch marks patch_submitted, but the current ADK run can still request tools. The native outer loop exits on final completion or when the current run returns. Public HARNESS_README's termination section explicitly qualifies its heading this way. A scripted continuation executes a real check and second submission after a successful first submission. Thus no configuration-only immediate per-tool termination guarantee is claimed. Injecting an end-invocation callback, modifying submit_patch, setting an untested tool-return policy or replacing the Runner would change the allowed submission path and is not done.

Progress labels are reasoning criteria: NEW_EVIDENCE may be a useful failure or negative search; VALID_REPAIR_PROGRESS requires a meaningful candidate revision supported by a distinguishing check; NO_INCREMENTAL_PROGRESS means no useful new information under materially unchanged conditions. No fixed revision count is imposed. Changing source, input, environment, hypothesis or a justified confidence requirement can make a retest useful. audit.py only labels controlled fixture signatures offline; it does not block the Agent or classify general command semantics.

Expected negative controls intentionally demonstrate residual risk: a noncompliant scripted model can repeat a check and submit twice. Passing those tests means the limitation was correctly observed, not that the unsafe behavior was prevented. Future GPU acceptance must count post-submit tool events, unchanged repeated commands, no-progress stretches and leftover diagnostics from actual traces. CPU-compliant scripts cannot establish autonomous adherence.

Command timeout cleanup is a separate gate from task deadline cancellation. The full CPU test waits a real120s command boundary, checks the actual long-running PID and verifies no delayed source write. Each candidate separately waits a real300s native deadline. A ten-second near-closure fixture is explicitly supplementary; it cannot substitute for either300s measurement.
